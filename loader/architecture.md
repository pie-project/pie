# Loader Architecture

> Target-state design for `loader/` (crate `pie-loader`), formerly
> `runtime/load-planner` (crate `pie-load-planner`). The move and rename —
> step 0 of §12 — have landed; everything else in this document has not.
>
> This document describes where the code is going, not where it is today.
> Citations of the form `path:line` refer to the **current** tree and exist to
> ground each claim in evidence. Sections marked *Today* describe what exists
> now and why it must change.
>
> The declaration format the driver hands to the loader — step 7b of §12 — is
> specified separately in [`spec.md`](spec.md).

---

## 1. Scope and position

The loader turns **checkpoint files on disk** into **weights resident in device
memory**, under a declared contract, in a way that is verifiable before
execution.

It is not part of the serving runtime, and nothing in `runtime/` calls it. Its
only client is the **driver**, its invocation point is cold start, and its
output is a durable artifact. It therefore lives at the workspace root, as a
peer of `driver/` and `runtime/`:

```
bootstrap/  bin/  client/  controller/  driver/
gateway/    interface/    loader/   runtime/   worker/
```

Two crates:

| Crate | Type | Purpose |
| --- | --- | --- |
| `pie-loader` | `rlib` | The whole loader: checkpoints, algebra, backends, verifier |
| `pie-loader-cbindgen` | `bin` | Emits the committed C header from `pie-loader`'s `#[repr(C)]` surface |

The second crate mirrors the existing precedent at
`interface/driver/cbindgen/`, whose manifest describes itself as a *"Decoupled
generator: emits the committed `pie_driver_abi.h` header from `pie-driver-abi`'s
direct local `repr(C)` surface via cbindgen."* The loader follows that pattern
exactly: a committed header, regenerated by an explicit command, with
`parse_deps = false` to keep the exported surface curated.

## 2. Design principles

These are the invariants the rest of the document derives from. Each one is
falsifiable; if a change violates one, the change is wrong.

**P1 — The loader never touches a device.**
No CUDA, Metal, or HIP call appears anywhere in `pie-loader`. The crate has zero
GPU dependencies and builds on any machine. `contract_writer.rs`,
`reference.rs` and `host_executor.rs` are behind the default-on `testkit`
feature, which `worker/Cargo.toml` disables with `default-features = false`.
This is what makes P2 and the paper's experimental setup possible.

**P2 — Backend lowering compiles unconditionally.**
`plan/passes/tile.rs` is *not* behind `#[cfg(feature = "cuda")]`. A GPU-less
CI machine compiles, lowers, and verifies CUDA plans. There is nothing to gate:
the module contains knowledge (which transform, which tile size), not calls.
The device-measured half of `TargetSpec` (§9) has no device to come from on such
a machine, so the loader must accept a `TargetSpec` assembled from recorded
values — a fixture, not a query. Backend-static fields need no such provision;
they are Rust constants already.

**P3 — The driver interprets; it does not decide.**
Every choice that affects which kernel runs on which bytes is made in
`pie-loader` and recorded in the plan. The driver's executor is a `switch` over
`kernel_id`. If the driver has an `if` that changes numerics, that `if` belongs
in `plan/passes/tile.rs`.

**P4 — Kernels stay in the driver.**
Transform kernels are shared with inference and carry numerical contracts with
it (§7). They are not moved, duplicated, or extracted.

**P5 — The plan is an artifact, not a message.**
The LOW IR is durable, cacheable, diffable, replayable, and signable. On the
normal path it lives only inside one `pie_*_load_model` call, but its content is
fully determined by the request and the compiler version, so the CLI can
reproduce, dump, and compare it offline. It is the unit of audit.

**P6 — The verifier does not trust the compiler.**
`verify` consumes the same plan the driver consumes, plus a contract the loader
did not author, and nothing else. Its independence is enforced by its argument
list: no compiler-internal type is in scope. §13 records how much weaker this
becomes once the plan is an in-process pointer rather than a byte buffer.

## 3. Layering

```
  worker  (bootstrap: config, launch, NCCL ids)
        │
        │  model path + policy
        │  (fp8 demotion, mxfp4 choice, TP topology, component)
        ▼
  runtime/engine/src/driver/              ← binder. pass-through.
        │                                   does not know loading exists.
        │  PieModelLoadDesc { snapshot_dir, policy }   (C ABI)
        ▼
  ╔════════════════════════════════════════════════════════════════╗
  ║  driver/{cuda,metal}/         C++. owns load_model end-to-end.  ║
  ║                                                                ║
  ║    authors its own contract + TargetSpec                       ║
  ║          │                                                     ║
  ║          │ ① pie_loader_compile_contract(...)  extern "C" →    ║
  ║          ▼                                                     ║
  ║  ┌──────────────────────────────────────────────────────────┐  ║
  ║  │ loader/     pure Rust · no GPU · no device calls          │  ║
  ║  │  checkpoint + contract → Expr specialize/infer → Lowering │  ║
  ║  │      → plan/build → plan passes → tile lowering → verify  │  ║
  ║  └──────────────────────────────────────────────────────────┘  ║
  ║          │ ② LOW IR (POD, zero-copy) + MemoryPlan              ║
  ║          ▼                                                     ║
  ║    allocate arena · walk instructions · mmap · staged H2D      ║
  ║    kernel_id → launch                                          ║
  ║          │                                                     ║
  ║          ▼                                                     ║
  ║    driver/{cuda,metal}/src/kernels/   shared with inference    ║
  ╚════════════════════════════════════════════════════════════════╝
```

Two boundaries are crossed, both inside the driver's own call stack. Neither the
engine nor the worker sees a plan.

### 3.1 Which component is "the driver"

`driver/{cuda,metal}` is the driver. `runtime/engine/src/driver/` is a binder:
it holds `enum DriverBackend { Dummy, Cuda, Metal, Remote }` and forwards calls
across the C ABI. It should forward `load_model(snapshot_dir, policy)` and know
nothing further.

*Today* it knows more than that, and so does the worker:

| Cold start | Hot path |
| --- | --- |
| `create`, `create_group`, `device_facts`, **`load_model`** | `register_program`, `register_channel`, `bind_instance`, `launch`, `encode`, `copy_kv`, `copy_state`, `resize_pool`, `close_*`, `export_kv_handle` |

`CudaDriver` (`runtime/engine/src/driver/backend/cuda.rs`, 446 lines) carries
both columns, but the engine uses only the right one. `load_model` is defined in
five places under `runtime/engine/src/driver/` and called from none of them —
its only callers are `worker/src/embedded_driver.rs:619` and `:683`, during
bootstrap, before `pie_engine::bootstrap` runs at all.

Worse, the plan itself was compiled up there: `compile_load_plan_bytes` and
`model_load_desc` sat in the worker's **bootstrap** module, whose actual job —
per its own doc comment — is "driver-backend bootstrap helpers": writing the
per-launch TOML each native driver reads at creation, generating NCCL unique
ids, and building a `DriverBackend`. Plan compilation landed there because the
snapshot path and driver capabilities happened to be in scope, not because it
belonged there.

**Resolved in step 2+3.** `compile_load_plan_bytes` is deleted and
`model_load_desc` is now a four-line constructor that copies the request through
unchanged. The worker's only remaining mention of `pie-loader` is
`PIE_LOADER_ENTRY_ANCHOR` (§3.4), which references the FFI purely so the linker
keeps it.

### 3.2 How C++ calls the Rust loader

The mechanism already exists in this tree; it just has not been used for the
loader.

**Reverse binding is an established pattern.** `runtime/waker/src/ffi.rs`
exports C symbols from Rust, and its module doc states the intent explicitly —
*"FFI — the only surface the other side of the boundary sees (B10): opaque `u64`
slot ids in, `0/1` out, callable from any thread, never unwinds."*

```rust
#[unsafe(no_mangle)]
pub extern "C" fn pie_wake(slot_id: u64) -> u8 { ... }
```

**The C++ driver is statically linked into the final Rust binary.**
`worker/build.rs:179` emits `cargo:rustc-link-lib=static=pie_driver_cuda_lib`
(and `:115` the Metal equivalent), under a module comment describing these as
*"`cargo:rustc-link-*` directives for the final binary"*.

Because both halves land in one binary, a `#[no_mangle] pub extern "C"` function
in `pie-loader` resolves for C++ callers at final link. No `cdylib`, no
`staticlib`, no duplicated Rust `std`. `pie-loader` stays `crate-type =
["rlib"]`.

The loader's surface is small:

```cpp
// loader/include/pie_loader.h  (generated, committed)
namespace pie_loader {
extern "C" {

PieLoaderStatus pie_loader_open_checkpoint (PieLoaderBytes           dir,
                                            PieLoaderCheckpoint**    out,
                                            PieLoaderDiagnostics**   out_diags);
void            pie_loader_close_checkpoint(PieLoaderCheckpoint* ckpt);

PieLoaderStatus pie_loader_compile_contract(const PieLoaderContractRequest* req,
                                            PieLoaderPlan**          out_plan,
                                            PieLoaderDiagnostics**   out_diags);
PieLoaderStatus pie_loader_verify_contract (const PieLoaderPlan*     plan,
                                            const PieLoaderContractRequest* req,
                                            PieLoaderDiagnostics**   out_diags);
void            pie_loader_release(PieLoaderPlan* plan);
void            pie_loader_release_diagnostics(PieLoaderDiagnostics* diags);

}  // extern "C"
}  // namespace pie_loader
```

The header is generated in cbindgen's **C++ mode**, not C. The linkage is still
plain C — `extern "C"` is emitted inside the namespace, so the six symbols are
unmangled and the ABI is unchanged — but the declarations are C++: scoped
`enum class`, and everything wrapped in `namespace pie_loader`. That
choice is not cosmetic. Both drivers are C++ and already spelled these types
`pie_loader::PieLoaderDType::BF16`; a C header would have forced
`PieLoaderDType_BF16` at ~95 call sites for no gain. There are no C consumers to
serve. The cost is that the header cannot be included from C, which is a cost
worth paying exactly until a C consumer appears.

The status code answers *did it work*; `PieLoaderDiagnostics` answers *what went
wrong*, as a flat array of records. Both entry points need it. `error.rs` today
carries structured `crate::error::Error` values (`Contract`, `Shard`,
`Checkpoint`, `Unsupported`, `Overflow`, `Internal`), and `verify` produces a
*list* of violations rather than a first failure — collapsing either into a single
`PieLoaderStatus` would discard the thing that makes verification worth running.
Diagnostics are also the honest place for non-fatal output, so a plan can compile
with warnings.

`PieLoaderPlan` exposes the LOW IR as POD arrays plus a `MemoryPlan`. The driver
walks it in place.

```cpp
// driver/cuda/src/loader/load_model.cpp
PieLoaderPlan*        plan  = nullptr;
PieLoaderDiagnostics* diags = nullptr;

// Three inputs, none of them a model's name: the tensor table, the program
// stated over it, and the device. `author_model_contract` reads the first to
// write the second (§10.2).
pie_loader::Checkpoint ckpt = pie_loader::Checkpoint::open(snapshot_dir, &err);
pie_loader::ModelContract contract;
pie_driver::author_model_contract(ckpt, facts, target, /*...*/, contract);

PieLoaderContractRequest req{ ckpt.get(), target_spec(target), contract.view() };
if (pie_loader_compile_contract(&req, &plan, &diags) != PIE_LOADER_OK) return fail(diags);
if (pie_loader_verify_contract(plan, &req, &diags) != PIE_LOADER_OK) return fail(diags);

void* arena = ctx.alloc(plan->memory.persistent_bytes);
execute(plan, arena);            // mmap · staged H2D · kernel_id → launch
pie_loader_release(plan);
```

### 3.3 What this simplifies

Putting the call inside the driver removes three awkward things at once.

**The plan stops crossing the ABI as an input.**
`PieModelLoadDesc.load_plan_bytes` (`interface/driver/src/local.rs:433-443`)
disappears, and `compiler_version` (`:437`) goes with it: that field exists only
so the receiver can check that the plan it was handed came from a matching
compiler, and the question cannot arise once the receiver compiles the plan
itself. The descriptor carries `snapshot_dir` and `policy`. The plan is produced
and consumed inside one call stack.

**The two-phase arena API disappears.** Arena size is an output of planning
(`MemoryPlan.persistent_bytes`), which previously forced a compile → allocate →
execute round trip through the caller. The driver now does all three itself.

**The capability cycle dies completely.** The driver has the device in hand when
it builds `TargetSpec`, so nothing needs to be reported outward and handed back.
The chain in §9.1 has no remaining step.

It also puts the contract where the kernels are: `driver/cuda/src/loader/
tensor_spec.hpp` already declares `TensorLayoutKind`, `TensorParallelKind`, and
`QuantFormat` in C++. That vocabulary stops being a parallel universe and
becomes the contract the loader is compiled against.

### 3.4 The cost

`driver/cuda` gains a build-time dependency on a generated header, and the final
link now has C++ → Rust symbol references in addition to Rust → C++. Link order
and archive-member selection need attention: the C++ archive's undefined
references to `pie_loader_*` must be resolvable from the Rust side of the same
link, which in practice means keeping `pie-loader` in the binary's dependency
graph even though no Rust code calls those entry points.

The specific hazard is worth naming, because "keeping it in the dependency
graph" is not automatic — and it has now been measured rather than guessed. A
`#[no_mangle]` symbol in an `rlib` survives only if the crate itself is
reachable; a `pie-loader` that no Rust code mentions is dropped before the C++
archive is ever scanned for undefined symbols. A staticlib built against
`pie-loader` with a dependency edge but **no reference** contains *zero* of the
four `pie_loader_*` symbols, `#[used]` table notwithstanding: `#[used]` keeps a
symbol inside an object file, but nothing pulls that object file into the link.

Two things are therefore needed, and both are in place:

* `pie_loader::ffi::entry::KEEP_ALIVE`, a `#[used]` array of the four entry
  addresses. This is what makes *one* reference enough — anchoring any single
  entry point brings all four, since they share the object file that holds the
  table.
* `PIE_LOADER_ENTRY_ANCHOR` in `worker/src/embedded_driver.rs`, a `#[used]`
  static holding `pie_loader_compile_contract`'s address. This is the reference. It is
  redundant today, because the worker still calls `pie-loader` for
  `compiler_version()`; it becomes load-bearing at step 2, when those calls go
  away. Deleting it then would reintroduce exactly the bug it prevents.

Verified: `nm target/debug/pie` lists all four `pie_loader_*` symbols as `T`.
The fallback, if the anchor is ever insufficient, is `-C link-dead-code`.

`driver/dummy`, being Rust, calls the loader directly as a normal crate
dependency — but per §10.3 it should not call it at all.

## 4. Responsibilities

| Concern | Owner |
| --- | --- |
| Checkpoint parsing (safetensors, GGUF) | **loader** — one implementation |
| Tensor contract (names, shapes, TP kind, quant format) | **driver declares**, loader consumes |
| Layout algebra, rewriting, type checking | **loader** |
| Kernel selection, fusion, tile splitting | **loader/backend** |
| Arena offsets, scratch placement, peak sizing | **loader** |
| Verification and certificates | **loader/verify** |
| Device context, allocation, streams, H2D | **driver** |
| Kernel implementations | **driver/kernels** — unchanged |
| LOW IR interpretation | **driver** — one `switch` |

In one line: **the loader decides *what*, the driver decides *how fast*.**

## 5. The two boundaries

| # | Boundary | Payload | Enforced by |
| --- | --- | --- | --- |
| ① | engine binder → driver (C ABI) | `snapshot_dir` + policy | `pie_driver_abi.h` (existing) |
| ② | driver → loader (C ABI, reverse) | request in, LOW IR + MemoryPlan + diagnostics out | `pie_loader.h` (new) |

Boundary ② is the one that currently fails silently, and fixing it is the
single highest-leverage change in this document. Note that ① loses
`load_plan_bytes`: the plan never appears in it.

### 5.1 *Today*: boundary ② is a hand-written parser

`driver/common/include/pie_native/load_plan.hpp` (868 lines) includes
`<nlohmann/json.hpp>` and calls `nlohmann::json::parse` at `:346`, then walks
`root.at("tensors")`, `root.at("sources")`, `root.at("buffers")`,
`root.at("instrs")` by hand into owning `std::vector`s.

Consequences:

* Renaming a serde field in Rust produces **no compile error**. It produces a
  runtime `nlohmann` throw, on a customer's machine, at model load.
* The C++ side re-declares constants that Rust owns. `load_plan.hpp:58-68`
  used to mirror `loader/src/load_plan.rs:10-20` by hand; the current constants
are `loader/src/plan/mod.rs:32-40` plus the backend masks in
`loader/src/plan/passes/tile.rs:31-42`.
* Every plan load pays JSON parsing cost.

To be precise about the scope of the fix: this removes JSON from the *load
path*, not from the driver. Of the 74 `nlohmann` references under `driver/`, 17
are load-related — `load_plan.hpp` (10), `load_plan_bridge.hpp` (1),
`safetensors_manifest.cpp` (2), and `metal/safetensors_view.cpp` (4) — and the
first two died here while the last two died with step 6, which deleted both
files. Nothing on the load path parses or emits JSON any more: the debug dump
that used to live in `load_plan_bridge.hpp` is rendered by `dump.rs` and arrives
as a string on the plan (§12 row 10). The remaining ~50 parse
HuggingFace `config.json` (§10.4) and per-launch driver settings, so the
dependency itself survives.

**But the consumer is already POD.** `LoadPlanExecutor::execute` takes
`const LoadPlanView&` (`load_plan_executor.hpp:65`), and `LoadPlanView`
(`load_plan.hpp:220-229`) is nothing but a version tag and `{ptr, len}` slices:

```cpp
struct LoadPlanView {
    std::uint32_t                version;
    PieLoaderSourceTensorSlice   sources;   PieLoaderTensorDeclSlice tensors;
    PieLoaderBufferDeclSlice     buffers;   PieLoaderStorageInstrSlice instrs;
    PieLoaderU32Slice            schedule;  PieLoaderMemoryPlanView   memory;
    // historical: deleted from the ABI (§12 row 15)
    PieLoaderOptimizerReportView optimizer;
};
```

The last member deserved a decision rather than a port, and got the wrong one.
`optimizer` carries compiler telemetry — pass names and rewrite counts — which
the driver read only to log. It is the one field that is neither an instruction
to execute nor a size to allocate, and the recommendation here was to keep it
*as a fixed header field rather than a variable-length slice*, on the grounds
that it costs nothing and the paper's measurements want it.

What shipped was the variable-length slice, and the logging reader went away
with the C++ executor. **It is deleted from the ABI** (§12 row 15). The
measurements are unaffected: the report still hangs off the Rust `LoadPlan`,
which is what `dump.rs` renders for the CLI, so what was removed is a copy
marshalled across the boundary for nobody. The lesson is narrower than "delete
telemetry": a field justified by a named reader has to be re-examined when that
reader is retired, and nothing made that happen — the reader's deletion and this
field's justification were in different files.

The owning `LoadPlan` exists only to be parsed from JSON and then produce
`view()` at `:352`. Nothing downstream of the view knows JSON happened. So the
JSON round-trip is a pure detour, and the executor is already written against
the target representation.

### 5.2 Target: `#[repr(C)]` POD + committed header

`loader/src/ffi/` holds the `#[repr(C)]` LOW IR types **and the four
`#[no_mangle] extern "C"` entry points** of §3.2, and is the only module cbindgen
reads. `pie-loader-cbindgen` emits `loader/include/pie_loader.h`, which is
committed to git. `cbindgen.toml`'s `[export] include` list is the curated
surface; anything not named there — `crate::contract::Expr`,
`crate::error::Error`, the plan-building types — cannot leak into the header
even by accident.

Because of §5.1, this is smaller than it sounds. `PieLoaderPlan` carries the same
members `LoadPlanView` already has, so the executor's parameter changes type and
**its body does not change at all**. The parser and the owning containers delete
themselves; the consumer is untouched.

That prediction held. Step 2 replaced the whole of `LoadPlanView` with
`using LoadPlanView = PieLoaderPlan;` and not one line of the executor changed.
`driver/common/include/pie_native/load_plan.hpp` went from 868 lines to 332: the
duplicated POD structs and the nlohmann parser are gone, and what survives is
RAII ownership of a Rust-allocated plan plus the POD helpers and
`LoadPlanIndex`, carried over byte-for-byte. Step 10 moved the file itself to
`loader/include/pie_loader/plan.hpp`, since none of what remained was specific
to any driver.

* The plan is flat arrays plus a header. The driver casts; it does not parse.
* `kernel_id` is a generated enum, namespaced per backend (`PieLoaderCudaKernel`,
  `PieLoaderMetalKernel`). A unified enum would force Metal to carry CUDA
  variants. The plan header carries a backend tag saying which enum applies.
* Adding a variant in Rust produces a **compile error** in the C++ `switch`.
* The header lives in git, so C++ builds never invoke cargo, and ABI changes
  appear as reviewable diffs.
* The entry points catch unwinds and return status codes, following
  `runtime/waker/src/ffi.rs`'s "never unwinds" rule. Detail travels beside the
  status in `PieLoaderDiagnostics` (§3.2), never as a panic.
* The entry points are callable from any thread and hold no global state, for
  the reason given in §6.3: tensor-parallel ranks already compile concurrently.
* Plan lifetime becomes explicit: the plan is borrowed from Rust for the
  duration of execution, and `pie_loader_release` runs after
  `cudaDeviceSynchronize`. Today the owning `LoadPlan` is a C++ local that
  outlives execution by construction, so this is a real obligation the current
  code gets for free.

No `cdylib` or `staticlib` is introduced. `pie-loader` stays `crate-type =
["rlib"]`, matching every other host crate in the workspace except
`sdk/python-server` and the wasm inferlets; the symbols resolve at the final
link because the C++ driver is linked into the same binary (§3.2).

## 6. Cold-start sequence

```
1.  worker bootstrap → engine binder → pie_cuda_load_model(snapshot_dir, policy)
2.  driver C++: build TargetSpec — backend-static consts
                + measured device values (SM count, smem, VRAM)
                + tp_rank / tp_size for this rank (§6.3)
3.  driver C++: build the contract it declares (from tensor_spec.hpp vocabulary)
4.  driver C++: pie_loader_compile_contract(&req, ...)   ─┐
       ┌─────────────────────────────────────────────────┘
       │  loader (Rust):
       │    parse checkpoint headers   (no tensor data read)
       │    specialize + infer `Expr`
       │    compile to `Lowering` runs and pieces
       │    `plan/build.rs` emits instructions
       │    `plan/pass.rs` runs arena/memory/rewrite checks
       │    `plan/passes/tile.rs` fixes tile rows and fusion
       └─→ PieLoaderPlan { instrs[], MemoryPlan { persistent, temp_peak, scratch_peak } }
5.  driver C++: pie_loader_verify(plan, &contract, &diags)  → status + diagnostics
6.  driver C++: ctx.alloc(plan->memory.persistent_bytes)
7.  driver C++: walk instructions → mmap sources
                → staged_pinned_h2d → kernel_id → launch
8.  driver C++: pie_loader_release(plan)
9.  driver C++: return capabilities; weights are resident
```

### 6.1 The plan declares the files it reads *(done — step 6)*

Step 7 of the sequence above says "mmap sources". Which sources?

`SourceTensorDecl::file_id` and `SourceExtent::file_id` are small integers, and
until step 6 the plan never said what they indexed. The driver recovered the
mapping by calling `discover_safetensors_manifest(snapshot_dir)` and taking the
result's order — a *second* enumeration of the checkpoint, written in C++,
against which the loader's own enumeration was never compared. Both sorted, so
both agreed; the agreement was a property of two implementations happening to
match, not of the interface. A divergence would not have failed loudly: every
offset would still have been in range, and the model would have loaded with
tensors quietly read from the wrong shard.

`LoadPlan` now carries the table:

```rust
pub struct CheckpointFileDecl {
    pub id: FileId,
    pub path: String,
    pub size_bytes: u64,
    pub format: CheckpointFormat,
}
```

Three consequences follow.

**The C++ readers stopped being parsers.** `CheckpointSource::open` takes the
plan instead of a directory, so CUDA's `safetensors_manifest.{cpp,hpp}` is gone
outright. Metal's `safetensors_view.{cpp,hpp}` — which discovered shards, parsed
every safetensors header, and served tensors by name — became
`checkpoint_source.{cpp,hpp}`, mmap plus `copy_storage_bytes` and nothing else.
This is the last place JSON was parsed on the load path.

Its name-addressed API (`get`, `try_get`, `has`, `names`, `size`) had no callers
left on the *load* path, but it did still have two under
`driver/metal/tools/rawmetal/`: `st_probe`, whose stated purpose was validating
`SafetensorsView` itself, and the `gemma4_decode_run` bring-up harness, which
staged weights by looking each one up by name. Both are deleted (966 lines).
Neither could be ported by renaming a type: they depended on resolving a tensor
name against a checkpoint *inside the driver*, and that capability is precisely
what §6 removes. A replacement would have to be handed a compiled plan, at which
point it is the production path rather than a harness. Both were macOS-only and
gated behind `PIE_METAL_BUILD_TOOLS` (default `OFF`), so no CI configuration
built them — worth noting as the reason this went unnoticed until a manual
grep, and as an argument for keeping tool targets in some build.

**Paths are absolute, and the plan is deliberately not relocatable.** The plan
was compiled against the headers of *these* files; a plan that pointed elsewhere
would be describing a checkpoint it never read. Relocatability is a property to
give the CLI's `replay` (step 9) explicitly, not one to get by accident from
storing a relative path.

**`size_bytes` makes staleness detectable.** Both readers now refuse a file whose
size no longer matches, and `verify` stats every declared file (§8.3). Size is a
weak proxy for content but a cheap one, and it catches the case that actually
occurs: a re-download or re-quantization under the same path. Nothing checked
this before, because there was nothing recorded to check against.

### 6.2 Why compile and allocate stay separate calls

Arena size is an **output** of planning, not an input. `MemoryPlan` computes
`persistent_bytes` during offset assignment, and the Metal driver allocates only
after reading the plan (`driver/metal/src/loader/heap_bind.cpp:133`).
`temporary_peak_bytes` and `transform_scratch_peak_bytes` have the same
character.

Previously this forced a two-phase API on the loader's *caller*, because the
caller was the one allocating. Now that the driver both compiles and allocates,
the split is an ordinary sequence inside one function — steps 4 and 6 of a
single `pie_cuda_load_model`. The loader still exposes compile and verify
separately, because verifying before allocating is the point.

### 6.3 Tensor parallelism

The sequence above is one rank. Tensor-parallel loads run it `tp_size` times,
and almost nothing new is required, because both halves already exist.

**The loader already shards.** `StorageTarget` carries `tp_rank` and `tp_size`
(`loader/src/plan/mod.rs:79-82`); a partition is written into the contract as
`Expr::Shard`, and `Resolver::specialize` (`loader/src/contract.rs:281`)
rewrites each one into the slice that rank reads, rejecting a dimension that
does not divide evenly and naming the tensor when it refuses. Below
`plan/build.rs` the expression means the same thing on every rank.
`TargetSpec` absorbs these two fields and the behaviour carries over
unchanged.

**The ranks already load in parallel.**
`runtime/engine/src/driver/backend/cuda.rs:331-345` spawns one thread per rank
inside a `std::thread::scope` and calls `load_model` on each. Three consequences
follow, and only the third is a design decision:

* **Thread safety is a requirement, not an aspiration.** `pie_loader_compile_contract`
  will be entered concurrently by `tp_size` threads on day one. It must hold no
  global mutable state — the same contract `runtime/waker/src/ffi.rs` states as
  *"callable from any thread, never unwinds."*
* **Compiling `tp_size` times is not a regression.** The worker already calls
  `compile_load_plan_bytes` once per rank. `loaded_model.cpp:339` describes a
  compile as costing tens of milliseconds, and the calls overlap, so this stays
  noise against checkpoint I/O. It is not worth optimizing, and sharing a
  compilation across ranks would be worth less than the coupling it introduces.
* **Ranks must not diverge, and the way to get that is structural.** Today each
  rank's descriptor is built from that rank's own `DeviceFacts` (`.zip(&facts)`
  in `worker/src/embedded_driver.rs:601-619`), so on heterogeneous devices two
  ranks could silently compile to different lowerings — a collective that
  disagrees about layout does not fail cleanly. **The leader builds one
  `TargetSpec` for the group; each rank substitutes only its own `tp_rank`.**
  Divergence then cannot be represented, which is the same move §9.1 makes
  against the `mxfp4_moe` rejection: prefer an unrepresentable failure to a
  detected one. The alternative — let ranks build their own and compare plan
  hashes afterward — adds a check where a constraint belongs.

## 7. Why kernels stay in the driver

An earlier draft of this design had the loader own its transform kernels, which
would let it execute end-to-end. That is wrong, for a reason worth recording.

The kernels are not loader-private. `slab_scatter` is used by the loader *and*
by `qwen3_5_forward.cpp`, `qwen3_5_moe_forward.cpp`, and
`recurrent_state_cache.cpp`. `quant_bf16_to_fp8` is used by the loader *and* by
`ops/gemm.cpp`. Others (`dequant_fp4`, `deinterleave`) are used only by
inference and never by the loader.

More importantly, they carry a numerical contract *with inference*.
`driver/cuda/src/kernels/quant_bf16_to_fp8.hpp:10-14` states it outright:

> *The scale convention matches what `ops::gemm_act_x_w` expects from a
> `QuantMeta` — cuBLASLt multiplies operand A by the scale pointer before the
> matmul, so storing `weight_scale_inv` (not its reciprocal) lets the dispatcher
> hand the same float to cuBLASLt unchanged.*

If a loader-owned copy of that kernel drifted from the inference-side
expectation, the result would be no compile error, no crash, and silently wrong
outputs — precisely the failure mode this subsystem exists to eliminate.
Duplication here is not a maintenance cost; it is a correctness hazard.

Since the kernels stay, the loader cannot execute, and the loader → driver
boundary must be **data**. This is what forces LOW IR, and it is also what buys
P1: a loader that does not execute has no reason to link a GPU runtime.

## 8. What LOW IR must guarantee

For the driver's executor to be a `switch`, the LOW IR must leave nothing to
decide:

* **Tiles pre-expanded.** No `for (row += rows_per_tile)` in the driver. The
  loop is unrolled into instructions at compile time.
* **Kernels named.** `kernel_id` plus typed parameters. No dispatch logic.
* **Addresses resolved.** Absolute arena-relative offsets. No address
  arithmetic beyond `base + offset`.
* **Scratch pre-placed.** No runtime allocation. Totals already exist as
  `transform_scratch_peak_bytes`.
* **Copies pre-batched.** Grouped exactly as `staged_pinned_h2d` wants them.
  The existing signature `staged_pinned_h2d(pool, const std::vector<StagedCopy>&)`
  (`driver/cuda/src/loader/staged_h2d.hpp:116`) with
  `StagedCopy { void* dst; const void* src; std::uint64_t size; }` (`:30-35`)
  is already the right shape.
* **No capability checks.** The planner guaranteed target validity; re-checking
  in the driver is either dead code or a divergence bug.

### 8.1 *Today*: the driver makes compiler decisions

`driver/cuda/src/loader/transcode_engine.hpp:827-862` makes three:

```cpp
// Fuse FP8 -> MXFP4 directly when possible, skipping the BF16 HBM
// round-trip. Bit-identical to the two-step (kernel parity-tested);
// opt out with PIE_CUDA_DISABLE_FUSED_TRANSCODE.
const bool fuse_fp8_mxfp4 = fused_transcode_enabled() && ...;

if (can_tile_encode(instr)) {
    const int rows_per_tile = encode_rows_per_tile(instr, source_dtype, rows, cols);
    for (int row = 0; row < rows; row += rows_per_tile) { ... }
}
```

1. **A fusion decision.** This is backend lowering. `plan/passes/tile.rs` now
   does this class of reasoning in Rust; here it was re-implemented in C++ at runtime.
2. **A tiling decision.** Tile size computed per instruction at run time.
3. **Scratch materialization.** `materialize_encode_input_bf16_rows` allocates
   on the fly.

And an environment variable, `PIE_CUDA_DISABLE_FUSED_TRANSCODE`, changes which
kernels run. **The same plan can execute two different kernel sequences, and the
plan does not record which.** Any claim that a plan determines execution is
false while that toggle exists.

Moving these into `plan/passes/tile.rs` fixes this by construction: fusion becomes a
`TargetSpec` input, is recorded in the plan, and therefore enters the plan hash.
The environment variable becomes a compile-time flag that produces a *different
artifact*, which is the honest representation of a different execution.

The existing parity test implied by *"Bit-identical to the two-step (kernel
parity-tested)"* is a ready-made safety net for this migration, and becomes a
differential experiment for the paper.

### 8.1.1 *Done* (step 5)

Two of the three moved; the third was already halfway across.

| Decision | Was | Is |
|---|---|---|
| Fusion | `fused_transcode_enabled()` — an env read per instruction | `plan/passes/tile.rs::encode_fusion`, recorded as `TransformSpec::fusion` and crossing as `PieLoaderStorageInstrView::transform_fusion` |
| Tiling | `can_tile_encode` + `encode_rows_per_tile` — 40 lines of arithmetic at run time | `plan/passes/tile.rs::encode_rows_per_tile`, recorded as `TileSpec::rows_per_tile` |
| Scratch | `materialize_encode_input_bf16_rows` | unchanged; `TransformSpec::scratch_bytes` already carried the size, and the allocation itself is a memory-plan question (§7), not a lowering one |

`PIE_CUDA_DISABLE_FUSED_TRANSCODE` is now read once per process, in
`fused_transcode_default()`, and reaches the loader as
`PieLoaderTargetSpec::fused_transcode`. It therefore reaches the plan, the plan
hash, `pie_loader_verify` (which rejects a plan compiled under the other
setting) and the artifact cache key. The claim in the paragraph above — that a
plan determines execution — is now true for this toggle rather than aspirational.

Three consequences worth naming:

* **The two branches of `encode_tile_map` collapsed into one.** `rows_per_tile
  == 0` means "the whole tensor in one pass", which is simultaneously the
  untileable case, the FP8 case and the case where one tile already covers
  everything. The driver no longer distinguishes them because the distinction
  was never about execution.
* **`max_tile_bytes` stopped crossing the boundary per instruction.** The driver
  states the budget in its request; sending it back beside the answer would only
  invite the executor to re-derive the answer. It survives in the Rust `TileSpec`
  because `host_executor` — a reference implementation, not a target — is
  allowed to decide for itself (§10.3).
* **The behaviour is unchanged on purpose.** `encode_rows_per_tile` is ported
  including its use of the *logical* dtype width for a quantized source, which
  overstates the true row cost. Reproducing the arithmetic exactly is what keeps
  the existing kernel parity test a valid safety net; changing the budget is a
  separate question with a separate experiment.

### 8.2 *Closed*: the coverage check was a tautology, twice

`driver/cuda/src/model/loaded_model.cpp` used to hold what looked like the
coverage guarantee this document keeps asking for:

```cpp
if (planned_load.covered_contract_count != planned_load.runtime_tensor_count) {
    throw std::runtime_error(
        "engine: Rust loader did not cover the full RuntimeABI; covered " ...);
}
```

But both fields were assigned from one variable in `load_plan_bridge.hpp`:

```cpp
const std::size_t runtime_tensor_count = view.tensors.len;
return { ...
    .covered_contract_count = runtime_tensor_count,
    .runtime_tensor_count   = runtime_tensor_count, ... };
```

The condition is `if (x != x)`. It cannot fire. What it actually asserts is
that the plan covers the tensors the plan declares — the loader grading its own
output, restated as a driver-side check.

This is precisely the gap §11 of `contribution.md` describes: a check whose
*form* implies a soundness argument that its *content* does not make.

The prediction above was that the check becomes real once the contract is
declared by the driver rather than derived from the plan. Step 7b-4b did that,
and the counts stopped being one variable — so the check moved to Rust as
`verify.rs::ContractCoverage::measure` and stayed.

**It was still a tautology, and phase 4 is what made that visible.** A ratio of
covered demands to stated demands is only informative when the demand list and
the plan have independent origins. After phase 4 the driver does not merely
*declare* the contract, it *authors* it — the contract is `compile`'s input, so
every demand is covered by construction and `measure` can only ever return
`n/n`. What survives is the check that was never circular: `check_contract`
compares each demand's name, shape and encoding against what the plan actually
produces, and a mismatch there is a real disagreement between two derivations.
`ContractCoverage`, `TensorDemand.optional` and the driver-side comparison are
deleted; the counting was the part that had no content.

The general lesson is worth more than the specimen: moving a vacuous check into
a stronger language does not make it say anything. The question to ask of a
coverage claim is not where it runs but whether its two operands were computed
by code that could have disagreed.

### 8.3 *Partly done* (step 8): what `verify` can already assert

Step 8 landed alongside step 6 — they share one FFI shape change — but only the
half that does not need a driver-authored contract.

**`pie_loader_verify` has callers now.** It previously existed as an entry point
nothing invoked. Both drivers call `plan.verify(request)` immediately after
`compile`. Verifying a plan the same process just compiled sounds circular, and
for the target fields it nearly is; it is not circular for the rest, because
`verify` shares no code with the compiler and because two of its checks read the
filesystem, which the compiler read at a different time.

Three checks were added:

| Check | Compares | Catches |
| --- | --- | --- |
| File staleness | `files[].size_bytes` vs `stat` | a checkpoint replaced between compile and load |
| Buffer coverage | `tensors[]` vs `Finalize` names | a declared weight nothing produces |
| Tile-map recognition | `target.tile_map_mask` vs `plan::passes::tile::*_TILE_MAP_MASK` | a driver claiming a transform the loader cannot lower |

The buffer-coverage check is the answerable half of §8.2, and it is the one that
outlived the contract count. It cannot ask "does the plan cover what the *model*
needs" — for that, see §8.2 on why counting cannot answer it at all — but it can
ask "does the plan cover what the plan itself declares", and the two operands
there really are independent: one is the declaration, the other is the emitted
instruction stream. A `TensorDecl` with no `Finalize` is a weight the driver
will look up and not find.

The tile-map check is what makes `plan/passes/tile.rs::tile_map_mask` load-bearing. The
driver remains the authority under §9, so a narrower mask is accepted: a driver
may implement fewer transforms than the loader knows how to lower. A *wider* one
is rejected, because the extra bit is a claim about kernels the loader has no
model of, and it would otherwise pass `validate_target_support` and surface only
as a failed kernel dispatch.

One risk this creates is worth naming: `verify` now runs on every model load, so
a check that is too strict does not fail a test, it fails every load. That is why
`a_real_checkpoint_compiles_to_a_plan_that_verifies` exists — the hand-built
fixtures are written to satisfy the checks, so only a real checkpoint exercises
what the compiler actually emits.

`covered_contract_count != runtime_tensor_count` in `loaded_model.cpp` was left
standing here deliberately, on the theory that it stops being a tautology once
the contract has an author other than the loader. It never did — see §8.2 for
why a count cannot become informative by changing who writes its operands — and
it is deleted.

## 9. TargetSpec

`TargetSpec` is data the driver declares. `plan/passes/tile.rs` is the backend
rule set that consumes it. The split matters:

* **Parameterizable → `TargetSpec`.** Alignment requirements, shared memory per
  block, SM count, supported quantization formats, fusion availability.
* **Not parameterizable → backend module.** Which `kernel_id` implements a
  given transform. The kernel *set* differs per backend, so this cannot be data.

This is the same division LLVM draws between target features and
`TargetLowering`.

`TargetSpec` mixes two kinds of field, and the distinction should be explicit in
the type:

* **Backend-static** — tile map masks, kernel sets, alignment rules. Compile-time
  constants in Rust. These never leave the loader and come back.
* **Device-measured** — SM count, shared memory, VRAM. Genuinely queried from
  the device. These legitimately flow in.

**Most of this type already exists**, as `BackendTarget` in
`driver/cuda/src/loader/backend_target.hpp`:

```cpp
struct BackendTarget {
    int device_major, device_minor;
    bool fp8_native;              // sm89+, for cuBLASLt's native FP8 GEMM
    bool gptq_marlin_int4;        // PIE_CUDA_HAS_MARLIN
    bool mxfp4_native_gemm;       // sm100+
    Mxfp4MoeLowering mxfp4_moe;
};
```

Built at `driver/cuda/src/model/loaded_model.cpp:155-174` from
`cudaGetDeviceProperties`, this is already the driver declaring its target. Step
3 is not inventing a type; it is moving an existing one **earlier**, so it
becomes a compilation input rather than a post-hoc filter.

### 9.1 *Today*: the loader's own constants round-trip as "capabilities"

```
loader/src/plan/passes/tile.rs:31-42            CUDA_TILE_MAP_MASK defined in Rust
  → driver/common/.../load_plan.hpp:58-68       kCudaTileMapMask, mirrored by hand
  → driver/cuda/src/context.cpp:660             reported as DeviceFacts.storage_tile_map_mask
  → worker/src/embedded_driver.rs:324           received back as StorageTarget
  → historical planner consumes it as a discovered fact
```

A Rust constant travels through C++ and returns disguised as a device
capability. The same pattern exists purely in Rust at
`worker/src/embedded_driver.rs:778` and `driver/dummy/src/lib.rs:305`. The file
`driver/metal/tests/caps_honesty_test.cpp` suggests someone already noticed.

The round-trip is one instance of a broader habit: a fact is restated in a
second language, and nothing links the copies. §5.1 has it for the tile-map
constants. `config.json` has it too — historical
`loader/src/inproc.rs:191-268` parsed six HuggingFace keys under a doc comment
saying it was *"mirroring the HF-key precedence in the C++ `parse_hf_config`
(`driver/cuda/src/loader/hf_config.cpp`)"*. That file does not exist; the C++
parser lives at `driver/cuda/src/model/config.cpp`. The mirror drifted and
nothing broke, because a hand-maintained mirror cannot break — it can only be
wrong. §10.4 covers that case. `loaded_model.cpp`'s tensor-parallel table was
the same habit at its most expensive: twenty-odd model types listed as
"shardable", then eighty lines re-deriving from `config.json` which dimensions
must divide by `tp_size` — all of it upstream of the loader, which partitions
the tensors and therefore *discovers* the answer. §12 row 11 deletes it.

The sharpest consequence is at `loaded_model.cpp:177-184`, where the plan
arrives *before* the device is characterized and is then validated against it:

```cpp
switch (load_plan.mxfp4_moe()) {
case PieLoaderMxfp4MoePolicy::NativeGemm:
    if (!backend_target.mxfp4_native_gemm) {
        throw std::runtime_error(
            "engine: LoadPlan requires native MXFP4 MoE, but this "
            "device/build does not provide it");
    }
```

The loader guessed a lowering strategy without knowing the device, and the
driver's only recourse is to reject the finished plan. Ordering the calls
correctly makes this unrepresentable: with `TargetSpec` as an input,
`plan/passes/tile.rs` selects the lowering it knows is available, and there is no
failure mode left to check for.

Moving the call site into the driver deletes the cycle outright rather than
merely reversing it: the driver builds `TargetSpec` with the device in hand and
passes it directly to `pie_loader_compile_contract`, so there is no outward hop for the
constant to make. Device-measured values still flow in; only the loader's own
constants stop pretending to be discoveries.

### 9.2 *Done* (step 2+3)

The cycle is cut. `kCudaTileMapMask` and `kMetalTileMapMask` are now defined in
terms of the generated `PIE_LOADER_TILE_MAP_*` bits rather than mirrored by
hand, so the C++ names are aliases of the Rust constants instead of a second
copy of them. Each driver states its mask in the request it compiles from, and
the loader honours it.

Everything the drivers used to re-check after the fact is gone:

| Deleted check | Why it is now unrepresentable |
| --- | --- |
| `loaded_model.cpp` — plan requires native MXFP4 but the device lacks it | `native_mxfp4_moe` is an input; `resolve_mxfp4_moe` picks a lowering the device has |
| `load_plan_bridge.hpp` / `heap_bind.cpp` — plan is not for this backend | `backend` is an input, and `pie_loader_verify` re-checks it |
| `load_plan_bridge.hpp` / `heap_bind.cpp` — plan uses transforms we cannot run | `tile_map_mask` is an input |
| `load_plan_bridge.hpp` — plan's `compiler_version` disagrees with ours | The plan is compiled in-process; there is no second version to disagree with |

The last one is worth naming: `compiler_version` used to guard a *serialized*
artifact that could outlive the compiler that wrote it. Nothing is serialized
any more, so the field survives only as an input to the weight-artifact cache
key, which is the one place a stale plan can still be observed.

That cache key needed rebuilding, and the reason is a good illustration of what
deleting a serialization format costs. The old key was `FNV(serialized plan
bytes)`, and the serialized plan embedded every source tensor's name, file,
offset, span, shape and encoding — so it was *accidentally* a content hash of
the checkpoint. Hashing only the request would have dropped that property
silently: two different checkpoints at the same path would share a key, and
`LoadedModel::load` skips the entire load plan on a hit, so nothing downstream
would ever reopen a file to notice. The key now hashes three things — the whole
compiled plan, the request facts no plan states (snapshot path, component), and
the size and mtime of every `*.safetensors` / `*.gguf` / `config.json` / index
file in the snapshot dir — and `artifact.rs`'s tests assert that mutating any
one of them moves the key.

Step 10 moved the key itself from `load_plan_bridge.hpp` into `artifact.rs`. It
had been CUDA-only; Metal had no key at all, despite its own comment saying a
false hit puts silently wrong weights on the device. Two things changed with the
move. The plan half is now mixed by serializing the *whole* `LoadPlan` rather
than by naming fields, so a field added anywhere is covered the moment it exists
instead of the next time someone remembers. That formulation is also the only
one that cannot be wrong by construction: the plan is the recipe, so a request
field changes the bytes only by changing the plan, and one that does not change
the plan cannot change the bytes. It is stable across runs because every
container in `LoadPlan` is a `Vec` — a `HashMap` anywhere under it would make
the key depend on iteration order, and would have to be mixed field-wise.
And `mxfp4_moe` is deliberately no longer hashed as *requested*: the plan carries
the *resolved* policy, and `Auto → RoutedDecode` produces the same bytes as an
explicit `RoutedDecode`, so sharing an entry is correct rather than a false hit.
Changing the digest invalidates existing cached artifacts exactly once.

The stat has to follow symlinks, and the reason is worth stating because the
obvious spelling does not: a HuggingFace snapshot directory is a farm of links
into `blobs/`, so `DirEntry::metadata` — which is `lstat` — reports the length
of the link target *string* (52 bytes for `config.json`, 76 for a shard, the
same for every model on the machine) and the link's own mtime. Read that way the
scan carries no information about the checkpoint at all, which is exactly the
failure the file-stat half exists to prevent. `an_edited_config_behind_a_symlink_is_a_different_key`
pins it; tests that write regular files cannot.

Two residual properties, both consequences of size+mtime being a heuristic
rather than a content hash, and both left as-is because the cache is out of
scope for this migration:

* An in-place rewrite that preserves size *and* mtime (`cp -p`, `rsync -t` over
  changed content) still hits. Strictly better than before, and the usual
  trade-off for not reading every byte to decide whether to read every byte.
* A mtime-only change (`touch`, a container rebuild, a non-`-p` copy) now
  churns the key, and the writer never evicts. Self-limiting only by the
  free-space guard in `weight_artifact_cache.hpp`, which declines to write
  rather than filling the disk. A real fix belongs to the cache redesign.

### 10.1 One crate, not five

An earlier draft split this into `api`, `core`, `verify`, `host`, and `cli`
crates. That was over-engineering. Crate splits are justified by differing
dependency sets, differing crate types, dependency cycles, or independent
publishing — none of which apply. Rust modules provide the layering.

* `verify` is a module, not a crate. Its independence comes from its
  **signature**: it takes the plan exactly as the driver sees it, plus a
  contract, and nothing else. It has no access to compiler-internal types
  because none are in scope in its argument list. If the paper later needs
  `cargo tree -p pie-loader-verify` as proof, the split is mechanical, because
  the boundary is already a data type. §13 records the limit of this argument.
* `cli` is `src/main.rs`. A crate can have both a lib and a bin target.
* `host` is a module. It is used by tests and by the CLI's `replay` command.

### 10.2 Naming: `ffi` vs `arch`

*Historical.* `src/abi/` was the *model architecture* guessing layer
(`nemotron.rs`, `qwen_moe.rs`, `gpt_oss.rs`, `fusion.rs`). That is "model ABI",
which collides with "C ABI" once a real C surface exists. The C surface is
`ffi/`, and it is the only one left: the model layer, renamed `arch/`, was
deleted whole in §12 row 12 phase 4 once contracts were declared rather than
inferred. The subsection below records what the three layers were, because the
reasoning is what made the deletion safe rather than brave.

#### 10.2.1 `abi/` is three layers, not one

"Which of this belongs to the driver?" is the wrong question to ask of `abi/`,
because it presumes one kind of knowledge. There are three, and they are the
three stages of a compiler:

| | Layer | What it is | Where it belongs |
| --- | --- | --- | --- |
| 1 | **Canonical layout expectation** | what a checkpoint of family *X* is expected to contain | the *input*. Ideally read, not predicted |
| 2 | **Contract** | what the runtime demands | the driver (§9) |
| 3 | **IR transform** | how to get from 1 to 2 | the loader (§5) |

Read that way, three things fall out that the flat reading hides.

**Layer 1 is already dead, and was never driver knowledge.** Nothing constructs
`RuntimeTensorSource::Semantic`. `arch::default_contract` is the only
builder, and it resolves names to `TensorId`s directly, emitting `DirectTensor`
exclusively — so historical `planner.rs`'s `needs_semantic_graph` check was always false
and `build_semantic_graph` was never called. `schema.rs` (28), `schemas/` (233)
and `semantic.rs` (90) were reachable only through a variant with no producer.
This is not knowledge to migrate; it is a bridge that was bypassed. Deleted
(step 7a), along with the `Semantic` variant, `SemanticId`, and the
`SemanticGraph` argument threaded through four historical `frontend.rs` functions.
`plan_from_semantics` is now `plan_from_contracts`, which is what it always did.

**`ArchProfile` (historical `abi/arch.rs`) mixed all three layers in one table** keyed by
`model_type`, with thirteen fields and exactly one consumer each — a dispatch
table wearing the costume of an abstraction:

* layer 1 — `source_prefix`
* layer 2 — `shard_axis_fn`, `shard_embed_tokens`, `replicate_lm_head`,
  `mxfp4_runtime_quant`, `bf16_runtime_quant`
* layer 3 — `mla_fused_joins`, `phi3_fused_splits`, `nemotron_packed_experts`,
  `gpt_oss_mxfp4_groups`, `skip_dense_qkv_fusion`, `stack_per_expert_moe`,
  `metal_qwen35`

**Layer-3 passes are gated by guesses about layer 2.** `fusion.rs:44` invents
the output name `model.layers.{L}.self_attn.qkv_proj.fused.weight` and trusts
that the driver binds it. Where that guess is wrong there is a flag; its own
doc comment gives the game away — Qwen3-MoE "bind[s] attention q/k/v as separate
tensors and never read[s] a fused qkv, so the generic join would consume
q_proj/k_proj/v_proj and leave the bind path with a `missing weight` error."

That is not an optimizer heuristic. It is a compiler pass second-guessing a
contract nobody wrote down. Once the contract is declared, the pass fuses iff a
fused output is demanded, and `skip_dense_qkv_fusion`, `stack_per_expert_moe`,
`phi3_fused_splits` and `metal_qwen35` have nothing left to say.

So step 7b did not "move `arch/` to C++". Layer 1 was deleted, layer 2 is
authored by the driver, and layer 3 **stayed in Rust and shrank** — because most
of what made it look model-specific was scar tissue from the missing layer 2.

That prediction held further than it was stated. With layer 2 written down, all
four remaining layer-3 gates had nothing left to say, and so did the passes they
guarded: `fusion.rs`, `phi3.rs`, `qwen_moe.rs`, `nemotron.rs`, `gpt_oss.rs` and
`metal.rs` were each a way of computing an expression the contract now simply
contains. What survived is `contract/rewrite.rs` — `coalesce_direct_row_shards`
and its helpers — which is layer 3 with no layer-2 guess in it at all: it
rewrites a contract into a cheaper contract, and asks nothing about the model.

One genuine decision looked like it survived, and it does not. Fusion appeared
to be a real optimizer choice: `dense_fused_projection_budget_bytes` notes that
"the unfused fallback binds non-owning views into the fused buffer", which reads
as though the driver accepts *both* shapes and the loader picks between them on
a byte budget. It does not.

`driver/cuda/src/model/workspace.cpp:26-29` comments `ws.qkv_fused` as **"Always
allocated"**, so the `!ws.qkv_fused.empty()` half of `use_fused_qkv`
(`llama_like/llama_like.cpp:463-464`) is a constant `true`, and the whole
predicate collapses to `layer.qkv_proj_fused != nullptr` — **a load-time
constant, not a per-batch decision**. What genuinely varies per batch is
`fused_decode_qkv_post` (`:466-478`), which merely requires `use_fused_qkv` as a
precondition. Consequently the unfused `else` branch (`:512-522`) is dead for
the entire lifetime of a fused load, and the q/k/v views built at
`llama_like/qwen3.cpp:99-105` are **never read** — their only remaining purpose
is to keep `L.q_proj` non-null for the `L.q_proj->dtype() == BF16` probe at
`:157`, which is itself circular, since `bind_projection_or_fused_view` only
produces a view when the fused tensor is already BF16 (`:41`).

So the contract does **not** need to express acceptable alternatives. Every
input to "should q/k/v be one buffer" — quantization scheme, TP degree, backend,
and kernel performance — is on the driver's side of the boundary; the 10 GB
figure in `fusion.rs:13-20` is an unmeasured guess at a heuristic whose own
comment concerns *kernel regression*, which §4/§9 make the driver's domain. The
driver decides and declares one shape, and views become something the loader
publishes for free because it already computed the offsets.

The declaration format that follows from this is specified separately in
[`spec.md`](spec.md).

**Where the contract is authored now.** `pie_loader::ModelContract`
(`loader/include/pie_loader/model_contract.hpp`) is the builder:
`define(name, expr).expect(shape)`, plus a constructor for each of the ten
algebra nodes and a `view()` of borrowed PODs for the FFI. The one non-obvious
thing about it is that the names, shapes and nodes are stored in `std::deque`s.
The PODs point *into* that storage, so a `std::vector` would invalidate every
already-built node on growth — a use-after-free that appears only above some
tensor count, which is to say only on large models. A test builds 512 tensors
and reads every one of them back.

Per-family authoring lives beside the forward pass that consumes it —
`driver/cuda/src/model/<family>/<family>_contract.hpp` — and is reached through
the `author_contract` hook on that family's arch-table row, next to its `bind`
and `create_model`. A contract and a binder are two halves of one sentence, so a
model type that has one and not the other cannot be expressed; a `model_type`
with no row is an *error*, not an empty contract.

It is per *backend*, not shared, because a contract is not a description of the
checkpoint — that is `source_facts`, which the loader reads. A contract says
what *this driver* wants in memory, and the two drivers want different things:
CUDA fuses projections for its GEMMs, shards across ranks and re-quantizes at
load time; Metal renames for MLX's binder and binds what the file holds. The
shared header made Metal carry CUDA's vocabulary — a `Component`, an MXFP4
policy and a runtime-quant request — through three call layers to an author that
read none of them.

Two properties of the contract are worth stating because they are not obvious.
First, **a declaration states only what the author knows**: `shape` is
`Option<Vec<i64>>`, so `define(name, expr)` without `.expect(...)` is a legal
and common thing to write. An author always knows the name and usually the
shape, but on AWQ/GPTQ/compressed checkpoints the weights are packed and often
transposed, and predicting the on-disk extents would turn a correct plan into a
violation. Encoding is different: it is *stated*, because the author is the one
choosing it — `plan/build.rs` inserts whatever `Cast`/`Decode`/`Encode`/
`Transcode` gets from what is on disk to what was asked for.

Second, **sharding is in the declaration** — as an expression, not as a shape.
`Expr::Shard` is the tenth node (§12 row 12, phase 1), so an author writes the
partition and not `rank * len`, and the rank-dependence is confined to one pass
that runs before inference. What `TensorContract.shape` states, when it states
anything, is the *rank's* shape, which is what `TensorDecl.shape` means too;
declaring the model-wide extent for a sharded weight would report a mismatch on
every rank.

### 10.3 `host` is not a production path

**Done.** `driver/dummy` used to execute plans through the host executor: it
held a `load_storage: Option<HostStorage>`, filled it from
`execute_serialized_plan`, and never read it again. The dummy driver opened real
checkpoint files, dequantized on the CPU, allocated host memory and discarded
the result — while forcing dummy-driver tests to depend on real snapshot
directories. It has no `pie-loader` dependency now, which took the
`HOST_TILE_MAP_MASK` round-trip and the `compiler_version` comparison with it.

`execute_serialized_plan` outlived its caller by two migrations, and with it the
whole serialize/deserialize path: `ffi/inproc.rs` existed so that a plan could
be handed across a process boundary as bytes. No caller ever did. Once the
contract crosses the ABI (phase 3) the driver holds the POD plan directly, so
the module is deleted and `LoadPlan` has no wire format — which is also what
retires `plan.version`, a number whose only reader was the deserializer's
compatibility guard.

With that gone, `host_executor.rs` and `reference.rs` are reference and test
infrastructure. They remain public — the CLI's `replay` needs them, and they are
the two halves of the differential test that gives the algebra meaning: one
executes a lowered plan, the other denotes the source algebra. Agreement between
them is the property worth testing.

### 10.4 The loader stops reading `config.json`

`config.json` is parsed three times today:

| Site | Reads | For |
| --- | --- | --- |
| historical `loader/src/inproc.rs:221` | 6 coarse fields (`ModelConfig`) | the storage compiler |
| `driver/cuda/src/model/config.cpp` (758 lines) | everything | inference |
| `worker/src/embedded_driver.rs:169` | `vocab_size`, `architectures[0]` | dummy startup TOML |

The obvious reading — "parsing belongs in the loader, so move it there" — is
wrong, because `config.json` is not one kind of fact. It carries two:

* **Checkpoint interpretation** — `model_type`, `quantization_config.quant_method`,
  `num_hidden_layers`, `num_experts`. Which tensors exist and in what shape.
* **Inference hyperparameters** — `rope_theta`, YaRN and Llama-3 rope scaling,
  `max_position_embeddings`, and `head_dim_kernel`, which `config.cpp:100-111`
  rounds up *to the nearest flashinfer-supported dispatch*. That is a kernel
  selection concern. Under §4 it is the driver's, and moving it into a component
  that by P1 never touches a device would be incoherent.

So the second kind stays where it is. But the first kind does not move into the
loader either — **step 7b removes the loader's need for it.** `schema.rs`,
`schemas/` and `semantic.rs` were three of the consumers, and step 7a deleted
them outright (§10.2.1): they were layer 1, and layer 1 had already stopped
being reachable. `compile_load_plan` lost its `ModelConfig` parameter in the
same change, since the semantic graph was its only use of it.

What remained was `arch.rs` and `arch/`, and there the config was used more
narrowly than it looks. Every surviving read is `num_hidden_layers` or
`num_experts` (`fusion.rs:41,134`, `qwen_moe.rs:81,107`, `nemotron.rs:9-31`),
and every one of them is a **loop bound for enumerating tensor names**. A
declared contract enumerates those tensors directly, so the loops iterate the
contract and the fields have no remaining reader. That is the whole of the
loader's dependency on `config.json`: not analysis, just counting things it
could have been told. Inference needed the config; declaration does not.

**This is now done** (§12 row 7b-4a). Because the reads were only counting, the
loader did not have to wait for full declaration: the driver states the five
facts on the request (`PieLoaderModelSpec`) and the loader opens no JSON on the
load path. Both drivers already had these values parsed for their own use — CUDA
in `HfConfig`, Metal in `ModelFacts` — so the loader's separate parse was
duplication that could disagree with the driver about the same file.
`parse_model_config` survived off the load path for a while, for the CLI, the
tools and the tests, which hold a snapshot directory and no driver — and then
phase 4 deleted it too, along with `ffi/inproc.rs` itself. Once nothing in the
crate is allowed to know what a model is, a parse of `config.json` has no reader
left: the CLI takes the contract as a file, because that is what lets it
reproduce *any* driver's plan rather than the one family it could have
reimplemented.

The target was that **the loader never opens `config.json`**. The
driver parses it once, uses one half to build the contract and the other half to
configure inference, and the loader sees only `contract + checkpoint +
TargetSpec`. The §9.1 mirror is not deleted so much as made unrepresentable —
the same move as the `mxfp4_moe` rejection and the rank-divergence constraint in
§6.3.

One residue is out of scope here but should not be lost: `read_hf_config_defaults`
(`worker/src/embedded_driver.rs:169`) infers a model type from
`architectures[0]` by lowercasing and stripping `forcausallm`. That is a fourth
copy of what `arch/` does, it lives in bootstrap, and step 0b is the natural
place to look at it.

Step 1 before step 2: the reverse binding is the one piece of this design with
real build-system risk (§3.4), so it was proven with the Rust half and a
generated header before the architecture came to depend on it. Step 2 is the
pivot — after it, "the driver calls the loader" is literally true and every
later step is local to one side.

Steps 2 and 3 were merged. They are separable on paper but not in code: the
moment the driver owns the compile call it must supply a target, and leaving
the old worker-side target in place through step 2 would have meant shipping
the device facts across the ABI only to delete that path one step later.

Steps 1 and 4 were merged. The original plan had steps 1-3 hand back serialized
bytes that C++ still parsed with `nlohmann`, with POD arriving only at step 4.
That interim state would have meant writing a marshaller twice, so the LOW IR
was made POD from the first call instead. The cost is that step 2 is now the
first step that touches C++ at all; the benefit is that no throwaway code was
written and the hand-written `PieLoader*` structs in `load_plan.hpp` are deleted
once rather than edited and then deleted.

Steps 7 and 8 are a pair. A coverage checker is only meaningful against a
contract the loader did not author (§8.2), so step 8 without step 7b would
reproduce the existing tautology in Rust. In practice the pairing bound step 8
to 7b-4b specifically, so `verify.rs` landed with the contract as an *optional*
argument: everything that does not need a driver-authored contract is checked
unconditionally, and the one check that does is live for the families that have
been declared.

### Why 7b-4b was split

*The split was right and the reason it gave was wrong.* Recorded as written,
because the correction is the useful part.

Full 7b-4b makes the driver the *author* of the contract and deletes the `arch/`
passes that guess at it. That is roughly 18k lines of binder across twelve
families, and the argument here was that it could not be validated: no
forward-pass test, few checkpoints, so a mistranslation in a family nobody can
run would surface as garbage output rather than as a failure.

What that missed is that a forward pass is not the only oracle. The old author
was still in the tree, so the two could be *compared* — and a plan is a value, so
the comparison can be exact rather than statistical. §12 row 12 phase 4 landed
authorship in one step behind a harness that diffs 2,240 plan dumps and cache
keys between the Rust and C++ authors and requires zero differences. The split
was still right: the declaration path built the FFI, the C++ vocabulary and the
`write_contract` round-trip that the proof then ran on. It was the prerequisite,
not the smaller version.

So authorship stayed in Rust and the *declaration* moved to C++. The driver says
what it will bind; the loader still builds the plan; `verify` compares two
answers derived by different code in different languages from the same
`config.json`. That is enough to deliver everything the split was for:

* `ffi/entry.rs` is handed a contract it did not author, which is what §8.2 asks
  for.
* `covered_contract_count != runtime_tensor_count` in `loaded_model.cpp` stops
  being `if (x != x)`.
* It is the safety net that has to exist *before* the `ArchProfile` gates can be
  dissolved — moving authorship with nothing checking the result is how a silent
  mistranslation gets in.

Adoption was per family and needed no flag day: `declare_model_contract` returned
an empty contract for anything not written out, an empty contract made the
coverage check `0 == 0`, and every other check still ran. Once authorship moved,
that escape hatch went with it — an unrecognized `model_type` is now an error,
because there is no second path for it to fall back to.

The declaration is checked against real checkpoints by exporting it. The C++ test
binaries cannot link `pie-loader` (it is an rlib consumed by the worker), so
`tests/model_contract_test.cpp` writes the *real* `declare_model_contract` output
to `PIE_TEST_CONTRACT_DUMP` and `ffi::tests::a_declared_contract_matches_a_real_plan`
reads it back. Transcribing the formulas into the Rust test instead would have
made it agree with a copy: the first transcription had already drifted from
`infer_qk_norm`, which treats `qwen3_5` as qk-normed and the copy did not. Because
the harness knows nothing about any family, declaring a new one is a change to
`driver/{cuda,metal}/src/model/<family>/<family>_contract.hpp` alone.

Writing the four declarations found three bugs that the tautological check could
not have: `declare_model_contract` dispatched on `qwen3_vl` while
`parse_hf_config` flattens a multimodal config to `qwen3_vl_text` (the family
silently declared nothing); the llama-like dispatch claimed `olmo3`, which
`registry.cpp` binds with `bind_row_olmo3` rather than `bind_llama_like`, and
omitted `llama3`, which it does; and `count_covered` excluded an absent optional
demand from the numerator but not the denominator, which would have refused to
load every tied-embedding checkpoint.

Note that `build.rs` hashes `src/` into `compiler_version`, so every step
invalidates cached plans by design.

## 13. Open tensions

**Backend knowledge enters Rust.** *Answered, and now enforced.*
`plan/passes/tile.rs` gives `pie-loader` opinions about CUDA. This is the
correct location — it is LLVM's `TargetLowering` — but it must stay
parameterized by `TargetSpec` data rather than `#[cfg]`, or P2 breaks and
GPU-less verification with it. Phase 5 of §12 row 12 moved the three constants
that had drifted back in (`FALLBACK_TILE_BYTES`, the encode scratch dtype, the
block-scale row count) onto the target, and
`tests/standalone.rs::the_backend_lowering_reads_its_ numbers_off_the_target`
fails on the next backend constant added outside `plan/passes/tile.rs`. The
one exemption is `TILE_MAP_MASK`, which is not a capability claim: it is the
set of transforms the *loader* knows how to emit, which the driver's own mask
is intersected with (§9).

**Verification independence weakens when the plan becomes a pointer.** P6 wants
`verify` to consume what the driver consumes and nothing else, and §10.1 rests
that claim on the argument list. Under §5.2 the argument is a `PieLoaderPlan*`
that the compiler allocated moments earlier, in the same process, from the same
allocator — so what survives is independence of *logic*, not of
*representation*. A verifier that re-reads a byte buffer could in principle
catch a serializer bug; this one cannot, because there is no serializer. That is
an acceptable trade for deleting the parser, but it should be stated rather than
inherited: the claim to defend is that `verify` shares no code path with
lowering, not that it shares no memory with it.

*Narrowed (§12 row 13).* There was a second, worse gap hiding under this one:
`PlanView` had two constructors — one from `LoadPlan`, one from the POD — and
the CLI used the first while the driver used the second, so a marshalling bug
was invisible to `pie-loader verify` and fatal in production. They had in fact
drifted, on how each derived `reads`. The `LoadPlan` constructor is deleted, and
every caller goes through `verify_marshalled`, which marshals into an arena and
verifies *that*. The marshaller is now on the path of every test in the crate,
so what is left unguarded is genuinely only the pointer hop the driver makes,
not the encoding step before it.

**The module tree recorded the pipeline the compiler used to be.** §12 row 15
fixed the names that were outright wrong and named three structural tensions
under them. Row 16 closed all three; they are kept here because the reasoning
that produced them is what should be applied to the next one.

*One algebra, two passes, two homes* — closed. `contract/` held exactly one
child while a 437-line sibling pass sat inline in the parent, which is also
why `enum Expr` and its builders sat 700 lines apart with the inference in
between. Both are passes over `Expr`; the directory was not small because
there was one pass, it was small because the other one was never moved.
`contract.rs` is now the declaration alone — grammar, types, builders — and
`contract/infer.rs` holds the checker. Inference and specialization stayed
together on purpose: they resolve names through the same `Scope`, and a
specializer that disagreed with the checker about what a name meant would be a
bug visible only at tp > 1.

*Three rewrite stages, three vocabularies, one report* — closed as far as it
should be. Contract-to-contract rewrites are `contract/rewrite.rs`,
physical-layout rewrites are `plan/passes/rewrite.rs`, and backend tiling is
`plan/passes/tile.rs`. `LoadPlan::passes` carries `Vec<plan::pass::PassStats>`
(`pass`, `instrs_before`, `instrs_after`, `rewrites`) with zero-rewrite passes
omitted, and `plan/passes/mod.rs::all()` is a single ordered list, so the plan
stages are one pass manager rather than three ad-hoc loops. The remaining split
is between the two IRs and is the one the thesis asks for: a contract pass
cannot run over a plan.

*Test support ships in the production library, ungated* — closed, and the
audit behind it was partly wrong. `host_executor.rs` (1,006 lines) is not a
fixture: `src/main.rs` replays plans with it. The genuinely test-only modules
are `contract_writer.rs` (246) and `reference.rs` (198). `#[cfg(test)]` is
unavailable because `tests/golden_plans.rs` and `tests/algebra.rs` link the
crate externally, so the route is a feature — `testkit`, default **on**, which
`worker/Cargo.toml` turns off with `default-features = false`. Default-on keeps
`cargo build` and the CLI working with no incantation; the one production
consumer opting out is what makes "nothing on the driver path reaches the
oracle" a build error instead of a convention.

**`TargetSpec` will accumulate.** Every backend-specific decision migrated from
C++ adds a field. The discipline is that each field must be either a
backend-static constant or a device-measured value, with no third category of
"flag the loader sets so the driver can check it". Phase 5 tested that
discipline and it held, but it also showed the cheaper move: `fused_transcode:
bool` became `fusion_mask: u32`, so the second fused chain is a bit rather than
a field. A capability that is one of a *set* should arrive as a mask; only a
capability that is a *number* deserves its own field. What the discipline does
not yet cover is that every field is an input the artifact key must include —
`artifact.rs` gets this right by mixing the whole target through serde rather
than a hand-written list, and that is the property to keep, not the field
count.

**Rank-uniformity is a constraint, not a check.** §6.3 makes the leader own
`TargetSpec` so tensor-parallel ranks cannot disagree. That works only as long
as nothing else per-rank leaks into compilation. The moment a second per-rank
input appears, the guarantee reverts to an invariant somebody has to remember,
and the honest response then is to compare plan hashes across ranks rather than
to hope.

*One appeared, and is now mostly gone (§12 row 14).* Phase 4 made the driver
author the contract, and `ContractBuilder::local_range` computed
`tp_rank * local` at authoring time — so for every family that splits a fused
source (llama-like QKV, Phi-3's gate/up, the MoE gate/up pair) the *contract*
was per-rank, which is precisely the second input. It sat next to `Expr::Shard`,
which exists to say the same thing without a rank in it, and in one function —
Nemotron-H's expert pack — both were used, on the two halves of the same weight.
The affine sites are ported to `Shard`; what is left is `Repack`, where a rank
genuinely cannot be deferred because `source_row_offset` is an integer a kernel
reads. So the leak is confined to the escape hatch rather than available to any
family, and `local_range` says so in its doc.

*And it is a check now.* `model_contract_test.cpp` authors at every rank of
every TP size and asserts the contract is byte-identical across them unless it
carries a `Repack` — which is the exception stated precisely enough that
anything else that starts baking a rank fails. Reverting the four ported sites
makes it fail, so it is not one of §8.2's tautologies. It was nearly one:
writing the assertion first showed the contract dump omitted the repack spec,
which would have made it blind to the only case it must not miss.

**Contracts must be declared somewhere.** *Closed (§12 row 12, phase 4).* The
driver authors, in `driver/{cuda,metal}/src/model/<family>/<family>_contract.hpp`,
reached through the arch table's `author_contract` hook; `arch/` is deleted. The worry recorded here — that the two vocabularies would
disagree — was answerable rather than speculative, and it was answered twice.
First by `write_contract`: the Rust side emits the same POD arena a C++ builder
emits, so all fourteen goldens assert `read_contract(write_contract(c)) == c`.
Then by the port itself, which was checked *before* it was landed, by diffing
2,240 (snapshot × backend × options × rank) plan dumps and cache keys between
the two authors and requiring zero differences. That is stronger than the
family-by-family plan this paragraph used to describe, and it is what made
deleting all 2,119 lines in one step defensible.

The honest statement of the residual risk is unchanged and worth keeping: **there
is still no forward-pass test here.** What the port has is byte-identity with
what `arch/` authored, on every checkpoint on this disk, which is not the same as
the model producing the right tokens. A family with no checkpoint on disk was
covered only by the code being the same shape as one that had.

**The reverse binding is the one build-system risk.** *Settled.* C++ → Rust
symbol resolution across a static archive depends on link order and
archive-member selection. It was proven with a trivial entry point at step 1,
and the whole driver has depended on it since step 2. The residue is a testing
gap rather than a build risk: the C++ test binaries under `driver/cuda/tests/`
cannot link the loader, because it is an rlib the *worker* consumes. Since
authorship moved to C++, `model_contract_test.cpp` needs the loader for real —
it opens a checkpoint to author against — so `driver/cuda/CMakeLists.txt` looks
for `target/debug/libpie_loader.a` (`cargo rustc -p pie-loader --lib
--crate-type staticlib`) and builds the target only when it is there. Skipping
one test is a better failure than breaking the build for everyone who has not
run that command. Under `PIE_TEST_CONTRACT_DUMP` the binary still exports its
authored contract as JSON, which is how anything needing the *compiler* reaches
it from the Rust side.

**The driver's Rust and C++ halves both remain.** This design does not collapse
them, and should not. The C ABI at `interface/driver` is the seam that lets
`driver/cuda` be built by CMake with nvcc while the rest of the system is cargo.
What changes is that the seam carries a model path instead of a compiled plan.
